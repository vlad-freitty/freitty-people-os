# Фаза 7 — Вхід за логіном і паролем: план

21.10.2026 · запит Влада: замість входу через Microsoft — email і пароль. Є один головний адмін, решті доступ видає
адмін: вводить email, ім'я, прізвище, роль і натискає «Згенерувати пароль». Пароль показується один раз, адмін
передає його працівнику, а після першого входу система вимагає змінити пароль. Статус: **план, не будуємо** (Влад
збирає правки).

## 1. Перший головний адмін

Без вебформи «зареєструватися», щоб ніхто чужий не міг стати адміном. Створюється командою на сервері (потрібен доступ
до сервера або бази):

```bash
npm run admin:create -- --email admin@freitty.com --first Ім'я --last Прізвище
```

- Команда створює користувача з роллю superadmin і друкує в консоль **одноразовий пароль**. Пароль ніде не
  зберігається відкритим текстом, у базі лишається тільки хеш.
- При першому вході система вимагає змінити пароль.
- Якщо суперадмін уже є, команда відмовляє (прапорець `--force` додає ще одного — для аварійного відновлення).
- Ця ж команда з `--reset` скидає пароль адміну, який його забув (теж лише з сервера).
- `SUPERADMIN_EMAIL` з env більше не потрібен.

## 2. Видача доступу (сторінка «Доступи», для адміна)

- **Форма:** email, ім'я, прізвище, роль → «Створити й згенерувати пароль». Модальне вікно «Пароль (показується один
  раз)» з кнопкою «Скопіювати».
- Якщо в системі вже є картка працівника з таким робочим email, доступ прив'язується до неї. Якщо ні — створюється лише
  користувач з ім'ям і прізвищем (див. питання 1).
- **Таблиця користувачів:** роль, статус, останній вхід, «Чекає зміни пароля». Дії: «Скинути пароль» (новий
  одноразовий пароль у тому ж вікні; старі сесії людини завершуються), «Деактивувати» / «Активувати», зміна ролі.
- Право `users.manage` — за замовчуванням лише superadmin, налаштовується в «Ролі й права».
- Аудит: `user.create`, `user.password.reset`, `user.deactivate`. Пароль у журнал не потрапляє ніколи.
- Охоронці, які вже є, лишаються: superadmin-роль видає лише superadmin, останнього superadmin не можна понизити чи
  деактивувати.

## 3. Вхід і зміна пароля

- Сторінка входу: email + пароль у дизайні з Figma (поля-пілюлі, червона кнопка).
- Після входу з одноразовим паролем будь-яка сторінка перенаправляє на «Змініть пароль», поки пароль не змінено.
- Вимоги до пароля: щонайменше 12 символів, не збігається з одноразовим, не з топ-списку очевидних паролів.
- Будь-хто може змінити свій пароль у профілі (потрібен поточний пароль).
- «Забули пароль?» — без листів: текст «Зверніться до адміністратора», адмін скидає пароль.
- **Захист:**
  - хеш паролів — scrypt (вбудований у Node, без нових залежностей);
  - 5 невдалих спроб → блок на 15 хвилин;
  - помилка однакова для «немає такого email» і «неправильний пароль»;
  - сесії інвалідуються при скиданні пароля чи деактивації (`User.sessionVersion` у токені).
- Dev-вхід (вибір тестового користувача) лишається лише локально.

## 4. Схема

```text
User  + firstName?, lastName? — для людей без картки працівника
      + passwordHash?, mustChangePassword (bool), passwordChangedAt?
      + failedLoginCount (int), lockedUntil?
      + sessionVersion (int) — збільшується при скиданні пароля / деактивації
```

`entraOid` і провайдер Microsoft — див. питання 2.

**Готово, коли (автотести):**

- адмін створює доступ → бачить пароль один раз → людина входить → її перенаправляє на зміну пароля → після зміни
  працює;
- скидання пароля завершує стару сесію;
- 5 помилок → блок, і повідомлення не розкриває, чи існує email;
- не-адмін не може створити доступ (403);
- superadmin-роль видає лише superadmin;
- `admin:create` відмовляє, коли адмін уже є.

## 5. Рішення Влада (21.10.2026)

| # | Питання | Рішення |
|---|---|---|
| 1 | Картка працівника під час видачі доступу | **Одразу все.** Форма «Новий доступ» створює і картку працівника, і доступ. |
| 2 | Вхід через Microsoft | **Прибрати повністю**: провайдер, `entraOid`, env `AUTH_MICROSOFT_ENTRA_ID_*`, рядок 1 у таблиці рішень CLAUDE.md. |
| 3 | Хто видає доступи | Superadmin **і HR**: `users.manage` за замовчуванням у ролях `superadmin` і `hr`. HR не може видати чи забрати роль superadmin (охоронець уже є). |
| 4 | Двофакторна автентифікація | Не потрібна. |

### Форма «Новий доступ» (одразу картка + доступ)

| Поле | Звідки | Обов'язкове |
|---|---|---|
| Email (робочий) | текст, унікальний | так |
| Ім'я, прізвище | текст | так |
| Роль у системі | довідник «Ролі й права» (`/roles`) | так |
| Відділ | довідник відділів (оргструктура); компанія визначається відділом | так |
| Посада | **вільний текст** (як і зараз) | так |
| Тип співпраці | штатний / підрядник | так |
| Дата старту | дата | так (від неї рахується PTO) |
| Прямий керівник | список людей | ні |
| Грейд | Senior / Middle / First-line Management, Individual Contributor (фаза 6) | ні |
| Локація | довідник локацій | ні |

Статус картки — `active` (або `onboarding`, якщо дата старту в майбутньому). Решту даних (документи, ставки) HR
доповнює в картці.

### Довідник ролей — уже є

«Ролі й права» (`/roles`) — це і є довідник «хто людина в системі». Системні ролі: Суперадмін, CEO, Керівник відділу,
HR, Legal, Фінанси, Адміністратор офісу, Користувач; у фазі 6 додається Head of People. Суперадмін може створювати
свої ролі (наприклад «Оператор», «Менеджер») і вмикати їм права. Роль відповідає за **права**, посада — за **назву
роботи** (текст), грейд — за **рівень** для PTO.

Влад, 21.10.2026: оператор і менеджер мають ті самі права, що й звичайний користувач — **окремих ролей не створюємо**.
Їм видається роль «Користувач», а «Оператор» / «Менеджер» пишеться в полі «Посада». Роль «Користувач» —
значення за замовчуванням у формі «Новий доступ».
